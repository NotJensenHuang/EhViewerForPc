# CPU 检索、扫描缓存迁移与本地目录兼容

日期：2026-11-15。接续 [上一轮真实索引验证](实际索引裁剪检索与补页修复-2026-11-14.md)，本文记录本轮最终实现与验证。

## 最终选择

- 按用户选择，检索只使用优化后的 CPU，不引入 GPU 检索；既有 ComputeSharp 建索引加速保留。
- 检索默认最多 8 个读取线程，不超过进程可见逻辑处理器数；CLI 同步支持 `--threads 1..8`。
- 图片索引格式、提取配置身份与已发布索引保持兼容，无需重建。
- 普通图片目录不要求 `.ehviewer` / `.thumb`，不向源目录生成元数据文件；应用缓存保存识别结果。

## 检索改动与真实结果

`DiskInvertedIndex` 使用有界块读取；Windows x64 将既有 48 字节小端记录直接解压到明确顺序布局的独占数组，仍逐条验证 ID 顺序及解压边界。`ImageSearchEngine` 按桶顺序读取，每块计时、每桶汇总，移除逐向量迭代器、计时和原子加法。Top-K、距离、评分及过滤保持原逻辑；中途取消、提前停止和异常均归还缓冲并关闭文件。

环境：Windows x64、i5-13600KF（14 核 / 20 逻辑处理器）、.NET 11.0.100。本轮构建与普通验证限制为 4 个进程可见处理器、低优先级；真实 AOT 检索使用用户指定的最多 8 个读取线程，并启用进程后台模式。未清空操作系统文件缓存，不作为物理冷盘基准。

真实索引仍为 `J:\Cache\EhviewerIndexCache` 的 `76a53b840fa141318facd76dbe152425`，435,605 页、163,119,136 条描述子、4,096 个中心。查询参数为 `NProbe=16`，对 `D:\BackUp\phoneGT5pro\ehviewer` 的五张第 3 页取中心一半宽高（约 25% 面积）。下表为新 NativeAOT 产物的完整服务耗时，含裁剪解码、提取、检索、清单匹配和文件核对。

## 为什么没有采用 GPU 检索

试验使用纯 C# / ComputeSharp / DirectX 12，未使用 CUDA。逐批上传的原型比 CPU 慢；常驻显存原型在同一首张样本上首次准备与检索为 44.65 s，缓存后为 1.24 s，占用约 5.6 GiB 显存。其完整候选与 CPU 一致，但偶发检索会承担较大的准备成本和显存占用。用户明确选择只保留优化后的 CPU，原型没有进入产品构建。

大规模原型还验证了资源数量边界，不能为每个桶长期分配独立缓冲；ComputeSharp 当前缓冲分配会取得两组描述符，分配器每堆上限为 4,096。该试验改用聚合缓冲后完成上述测量。相关源码依据为 [缓冲分配](https://github.com/Sergio0694/ComputeSharp/blob/v3.2.0/src/ComputeSharp/Graphics/Resources/Abstract/Buffer%7BT%7D.cs) 和 [描述符分配器](https://github.com/Sergio0694/ComputeSharp/blob/v3.2.0/src/ComputeSharp/Graphics/Commands/Interop/ID3D12DescriptorHandleAllocator.cs)。这些原型限制不影响最终 CPU 检索。

原始试验证据保存在 `.qa/gpu-query-20261114/backend-gpu-compare.log`、`backend-gpu-large.log`、`backend-resident-slabs.log`，试验源文件在已忽略的 `prototype/`，没有新增磁盘索引副本或产品依赖。

## 扫描缓存为何曾被整体失效

上一轮将扫描缓存 schema 3 升为 4，旧加载器对版本不相等的文件返回空缓存，导致所有目录都要重新解析。现在兼容读取 schema 3，保留普通条目；仅含空文件或旧页数诊断的条目强制重算，其他未变化条目继续命中缓存。未扫描的旧缓存再次保存时保留 schema 3，防止丢失语义标记；扫描器完成后输出 schema 4。

缓存首屏与后台签名核对继续存在；此次改动避免按版本整体丢弃缓存，并不取消正常的目录签名核对。普通图片目录的新命名标志直接加入现有源生成缓存模型，不再提升整个缓存版本。

## 补页等待进度

根因为新补页任务的 `DownloadedPages` 默认 0，直到获取网络页清单后才核对已有页。现在入队校验原目录有效的原始页号，并把已有页数作为等待阶段的进度；计数去重且排除已知总数之外的页。获取网络清单前再次核对，保持既有页跳过逻辑。

旧任务启动后由下载服务持有的单个后台任务修正计数，保留等待 / 暂停 / 失败状态，不额外启动下载；退出取消并等待在途读取。队列保存失败时回滚计数。原生合成验证为 51 个有效页 / 53 页，等待进度环值 **0.96226**；重启保留计数，旧零计数任务也能修正。

## 普通图片目录

- 支持 JPG / JPEG / PNG / GIF / WebP 普通文件名及自然数字排序，例如 `Image00000.jpg`、`page2.png`、`page10.png`。
- 无元数据的普通目录使用完整目录名作为标题，避免把年份等数字前缀误识别为在线 GID；首张图作为封面，相同主文件名的不同格式作为候选。
- 使用连续应用内页号，不凭普通文件名的数字间隔推断缺页；没有权威总数时保留「未知原始总数」语义，真实空页仍可诊断。EhViewer 编号与有效元数据来源继续保留原始缺页位置，额外封面不扰乱编号。
- 扫描、阅读与索引保持源文件只读，既不生成 `.ehviewer` / `.thumb`，也不改名、移动或删除。

实际只读验证用户指定的 `D:\BackUp\phoneOnePlus7\ehviewer\momi` 下普通漫画目录：**23 页**，首图 `Image00000.jpg`，没有 `.ehviewer` / `.thumb`，不属于缺页；首尾 JPEG 解码和阅读页号均通过，目录内全部文件的路径、大小、mtime 前后相同。另以原生合成目录验证自然页号与以图搜图命中页号一致。
