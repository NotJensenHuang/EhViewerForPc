# 本地以图搜图索引加速方案（2026-11-13）

状态：方案评估，尚未实施计算后端优化。按用户要求，在卡片、导航与滚动加载改动完成之后评估。前置交付与证据见[在线卡片与滚动加载验证](在线卡片与滚动加载验证-2026-11-13.md)。

存储与恢复已随后重设计，见[索引共享存储与断点恢复](索引共享存储与断点恢复-2026-11-13.md)：特征改为单份共享缓存、增量文件优先硬链接、任务支持恢复。本文中计算流水线、SIMD 与 GPU 仍属于待实施方案。

## 环境与结论边界

只读硬件查询得到 Intel Core i5-13600KF（14 核 / 20 逻辑处理器）、NVIDIA GeForce RTX 5070 Ti。本次没有运行真实图库性能采样、GPU 负载或 GPU 兼容性验证；未确认可选 CUDA 运行库的安装与部署条件。先前为了后台验证设置的 `DOTNET_PROCESSOR_COUNT=2` 只作用于验证子进程，不是应用建库的持久设置，也不能作为索引性能基线。

以下“优先级”来自实际调用链与实现约束，属于待测的工程判断，不代表已经测得哪个阶段占主要时间，不承诺加速倍数。

## 当前实现的具体限制

1. `Services/LocalImageSearchService.cs` 的 `Build` 逐页串行执行读取、灰度化 / 缩放、规范化 PNG 编码、哈希、ORB 提取、`ImageDatabase.Add` 与清单写入；整个任务只有一个 `Task.Run`，并未按页并行。
2. `ImageSearch/ImageImporter.cs` 的独立导入器虽支持两个 worker，但 `canvas = new SemaphoreSlim(1, 1)` 明确限制一次只有一张图片持有解码 / 提取画布；应用内建库也没有调用该导入器。单纯增加 worker 数量并不能绕过这一限制。
3. `GrayImage.Decode`、`Resize` 与 `OrbExtractor.Blur` 含逐像素托管循环；ORB 还要构造 8 层金字塔、检测 FAST、分布角点并计算旋转描述子。
4. `ImageDatabase.Add` 每张图片打开 SQLite 连接并开始 / 提交事务，清单也逐行创建 SQL 命令与插入。存储重设计后，增量更新仅复制元数据，特征全局共享，不可变文件优先硬链接；完全无变更仍会核对页面并重建物理副本映射。
5. `BinaryKModes` 的分配 / 中心更新及 `ImageSearchEngine.Build` 中的量化分桶主要串行。当前哈明距离已经使用四次 `BitOperations.PopCount`，应先检查实际机器码和测量结果，不能把它当成完全没有底层优化。
6. 当前缓存身份基于 `canonical-png-gray8-v1`，提取器为 `managed-slam-orb-v1`，所有参数进入 `FeatureProfile.Id`。更换算法、插值或规范化哈希必须处理索引兼容性。

## 推荐实施顺序

### 0. 建立分阶段基线

对固定只读样本分别测量枚举 / 缓存核对、读取解码、灰度化缩放、规范化编码与哈希、ORB、SQLite / 描述子写入、训练、分桶 / 合并、快照复制 / 发布。

先用少量代表页确认测量边界，再扩大到固定样本。分别测试首次全建、无变更更新、少量新增 / 删除更新；区分冷 / 热缓存、普通页 / 长图，报告页每秒、阶段耗时、CPU 使用率、峰值内存和写入量。保留相同样本和配置，比较 Release / AOT，不用 Debug 或合成图库结果替代实际图库结论。

### 1. CPU 流水线与写入批处理（最高优先级）

- 采用有界 Channel：读取 / 缓存核对 → 多个独占画布的提取 worker → 单一写入者。以“解码像素与金字塔实际预算”限制并发，而非只数任务；保留 UI / 阅读图片的内存额度。
- 先比较 2 / 4 / 6 个提取 worker；后台默认建议从 2–4 个开始，依据实际内存、磁盘与交互延迟再选值。保留可取消、迟到结果丢弃、异常观察与退出等待；不直接开满 20 线程。
- 每个 worker 独立拥有解码 / 金字塔缓冲与提取器，不跨线程共享可变画布。结果队列必须有背压，避免把已提取数据无限堆在内存。
- 写入者复用连接和预编译语句，按有界批次提交 SQLite 事务，同时协调描述子文件、清单和检查点。取消或崩溃只能丢弃未发布的新代，不能损坏当前索引；不通过取消持久化保证来换速度。
- 无变更更新直接结束，少量变更最大化复用描述子、量化器及未变更索引段，减少全量快照复制。
- 规范化 PNG 只在确实需要时生成 / 复用。若改为对版本、尺寸与灰度像素计算规范化哈希，升级 normalizer 身份并生成新索引代，不能悄悄混用旧缓存。

### 2. SIMD 与训练并行（保留现有算法）

优先测量灰度转换、两遍高斯模糊、缩放与批量阈值比较，再决定哪些循环使用 `Vector256<T>` / 平台指令。对齐、尾部像素、EXIF、透明度合成、边缘反射与舍入必须和标量参考路径一致；通过运行时支持检查提供标量及其他架构回退。

训练中的样本分配、桶内中心统计可以按分区并行，并进行确定性归并；分桶可使用 worker 独占桶缓冲后归并。保持相同输入下的稳定 tie-break、索引签名与取消边界，避免无约束的内外层嵌套并行。

`BinaryDescriptor.Distance` 已经使用 PopCount。单个 32 字节描述子不一定值得换成更复杂的 SIMD；应对批量距离计算测量后再选实现。

.NET 的 SIMD / 硬件指令接口及回退规则参考 [Microsoft 官方说明](https://learn.microsoft.com/en-us/dotnet/standard/simd)。

### 3. RTX GPU 后端（可选，高成本验证项）

现有 ORB 为手写托管代码，接入 GPU 需要单独实现或封装 GPU 算法。可以先做 CUDA ORB 的小型原型；OpenCV 提供 [cv::cuda::ORB](https://docs.opencv.org/4.13.0/da/d44/classcv_1_1cuda_1_1ORB.html)。

- 先比较整个流程的解码、上传、GPU 提取、回传及入库总时间；不能只测 kernel。尽量使缩放、模糊和特征提取留在 GPU，并按有界批次处理，避免每张图反复分配、上传和同步。
- GPU 训练原型可评估二进制描述子的中心分配 / 统计。当前索引为二进制特征和哈明距离，不能直接把面向浮点向量的 GPU 索引当成同格式替代物。
- 推荐由 `ImageSearch.Host` 隔离可选原生依赖和 GPU 故障，通过明确的任务协议向应用报告进度 / 取消；需要评估 CUDA、OpenCV 构建、驱动 / 架构兼容、NativeAOT 的静态 P/Invoke 边界和打包体积。
- CPU / GPU 的 ORB 实现可能在灰度、金字塔、角点分布、方向和描述子上不同。GPU 索引必须有独立 `FeatureProfile` 与新索引代，查询使用对应提取器；不能保证 CPU 查询器可直接接替 GPU 提取器。可回退到保留的 CPU 索引，或实现并验证等价的 CPU 路径。
- 背景 GPU 作业需限制批次、显存与排队，验证阅读动画 / 桌面交互延迟。支持 CPU 路径，跨平台发布不能强制依赖 CUDA。

## 验收标准

- 相同源库的路径、大小和 mtime 快照不变；现有索引在取消、失败和崩溃后仍可搜索。
- 无变化更新跳过特征提取；少量新增 / 删除正确更新所有来源与物理副本映射。
- 并发与 SIMD 等价实现通过标量对照、固定描述子金样、长图 / 透明图 / EXIF / 损坏图和边界回归；更换提取器则独立报告召回率，验证跨裁剪、缩放与截图样本。
- 报告总建库时间、各阶段耗时、峰值内存及查询 / UI 延迟。GPU 另报告传输与执行时间及显存，不将 kernel 提速当成总流程收益。
- 使用全新 AOT 产物实际运行；保留 CPU 路径与 Linux 托管发布验证，未实机的平台明确列出。

建议先落地 0–1，再以结果决定 SIMD 热点和 GPU 原型是否值得继续。日常操作优先用“建立 / 更新索引”；“重新提取重建”会重新计算页图特征，适用于需要重建的情况。
