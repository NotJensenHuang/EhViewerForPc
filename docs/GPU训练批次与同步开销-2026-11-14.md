# 训练阶段 GPU 低占用：批次与同步开销（2026-11-14）

用户确认低 GPU 占用发生在“正在训练图片索引”，不是提取页图。本记录更新[首版 ComputeSharp 实施](ComputeSharp与持久化恢复实现-2026-11-14.md)的训练性能结论；不把旧版整个建库的 384 页样本当作此处训练阶段的数据。

## 诊断边界与复现

全程后台限 2 个逻辑处理器、低优先级进程；仅生成独立描述子数组，不读取真实资料库 / J 盘特征库，不附加或暂停用户的阅读器，也不操作桌面。环境为 Windows x64、.NET 11.0.100、NVIDIA RTX 5070 Ti。AMD / Intel 未实机验证。

使用原 `BinaryKModes.Train` 二级训练，固定种子 42 生成 1,500,000 个 256 位描述子，4,096 个中心、最多 10 次迭代、2 个 worker；GPU 包装器只计时真实 `TryAssign` 调用，失败回退即判测量无效。每次 GPU 训练最终中心、频数和总距离逐项与同进程 CPU 对照一致。原始工程与日志在 `.qa/training-gpu-20261114/`。

按顺序核对三个假设：CPU 中心位统计、小分组阈值、频繁传输 / 回读。初始 JIT 复现中 CPU 1.83 s，GPU 4.17 s，确有训练回归，不能用“GPU 没吃满属于正常”略过。原 GPU 路径的两轮 .NET 线程采样中，属于 GPU 训练调用树的采样时间约 65.7% 落在 `TryAssign`，约 27.3% 落在 CPU `UpdateCenter`；详见 `large.speedscope.json`。这是线程栈时间采样，包括同步等待，不是硬件 CPU 或 GPU 忙碌率，也不是不加区分的全进程百分比。

`TryAssign` 的旧布局每批最多 8,192 个描述子：上传中心，再分块上传数据；每块分别回读归属和距离。二级训练常见约 64 个中心，此时旧块仅约 0.5M 次比较，低于既定的 8M 单 dispatch 上限；大量小命令和同步传输让显卡工作断续。GPU 路径还保留 CPU 的计数 / 有序分组和中心位统计，`ImageSearchEngine.Train` 另外包括训练样本读取和串行 HNSW 构建，因此整个“训练”阶段并未完整迁入 GPU。

26.2 万描述子较小样本中，只有 4 次 `TryAssign`，大量局部分组因低于 1,048,576 次比较留在 CPU，暖态 GPU 主机调用只占训练墙钟时间约 11.8%。150 万样本中则有 708 次 GPU 调用：两类规模的瓶颈不同，不能只看“启用了 GPU”推断大部分训练已卸载。

## 本次修改

- 描述子固定容量提高到 131,072，仍按 `min(容量, 8M / 中心数)` 缩小每次 dispatch。最大单命令比较量维持 8M，不通过无限延长 kernel 提高表面占用率。
- 将本块描述子与中心打包到一个基础 `uint` 缓冲，只上传一次；归属和距离打包到一个基础 `int` 缓冲，只回读一次。中心和距离的偏移都使用实际尾块长度。
- 保留 CPU 的确定性距离归并、相同距离最小中心序号、位统计和平票规则，不改变提取配置或索引格式；GPU 失败完整重算当前分配。取消仍等已提交命令完成后归还池化数组。
- 训练设备缓冲约 5.125 MiB，加上已存在的最大 FAST 缓冲后总上限约 26 MiB。主机池化字缓冲可能因桶舍入占 8 MiB，结果缓冲 1 MiB；已有 32 MiB 共享 GPU 暂存预算仍覆盖它们。驱动资源及进程 RSS 不由这个数字代表。

两个变量分开测量：只扩大容量时，JIT GPU 训练降到 2.35–2.50 s；合并传输后降到 1.84–2.28 s。这些只是诊断过程，正式比较使用下述同一 AOT 验证器，未将 JIT 与 AOT 混算。

## NativeAOT 对照

隔离验证器同时编入 `073beea` 的旧 GPU 类（仅更名，保留原 shader）和当前 GPU 类，同一份当前 `BinaryKModes`、数据、随机数及 worker 配置。分别启动两个进程，每个先预热一次小分配，再做一次 CPU 参考和两次完整 GPU 训练；旧 / 新 GPU 均通过中心 / 频数 / 距离等价检查。未将不同方法的随机训练结果作为对照。

| 路径 | 完整训练 s | GPU 主机调用 s | dispatch | TryAssign 调用 | 距离比较次数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| CPU（旧 GPU 对照进程） | 2.048 | 0 | 0 | 0 | CPU |
| CPU（新 GPU 对照进程） | 2.043 | 0 | 0 | 0 | CPU |
| 旧 GPU，轮 1 / 2 | 2.781 / 2.779 | 2.005 / 2.006 | 2562 | 708 | 1,173,477,974 |
| 新 GPU，轮 1 / 2 | 1.327 / 1.360 | 0.568 / 0.583 | 719 | 708 | 1,173,477,974 |

这个合成训练场景中，新 GPU 两轮平均总耗时较旧 GPU 减少约 52%，较本次 CPU 对照减少约 34%。源日志为 `aot-old.stdout.log` / `aot-new.stdout.log`。样本量为每种 GPU 两轮，不外推所有图像分布、更多 worker 或真实全库；进程峰值 / 硬件 GPU 利用率没有在本轮测量。

GPU 主机调用时间包含上传、命令提交、fence、回读和 CPU 打包，不能将 0.57 s / 1.34 s 写成 GPU 占用率。此次确认的是更少的同步开销和更短的训练时间；没有证据承诺 GPU 会达到 100%。CPU 位统计与每轮重新传入数据仍存在。后续若继续卸载，应优先采用训练数据设备常驻和整数位统计 / 中心更新，在 CPU 金样等价下逐项推进，而不是单独拉低小分组阈值。

通过 `tools/imsearch/Process.ps1` 的 `Invoke-ImsearchProcess` 后台运行新验证器，参数分别为 `1500000 10 old` / `1500000 10 new`。未提供模式时为新 GPU。`probe/LegacyComputeSharpAccelerator.cs` 从 `git show 073beea:src/EhViewerForPc.ImageSearch/ComputeSharpAccelerator.cs` 生成，只替换类名。不要直接将命令解释器字符串拼成应用参数。

采样使用本机 `dotnet-trace` 9.0.661903 的 `dotnet-sampled-thread-time` 配置和 32 MiB 采样缓冲；本版本 `cpu-sampling` 仅用于 Linux 子命令，最初误用该配置的调用未启动样本，已记录为 `profile.*.log`，有效采样是 `large-profile.*.log`。发布验证器本身的 Windows 平台分析提示来自隔离旧类的显式选择，产品仍有 Windows 守卫；AOT 实际硬件调用通过。
